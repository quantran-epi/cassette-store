# Phase 03 - UI Design Contract

> Visual and interaction contract for Phase 3: Fast Order and Shipping Workflows. Generated by `gsd-ui-phase`, verified against the phase context, research, and current Ant Design implementation.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | Ant Design 5 through local wrappers in `src/Components/` |
| Icon library | `@ant-design/icons` |
| Font | Existing app font stack for body; keep Kanit only where the app shell already uses it |

### Component Contract

- Use existing local wrappers first: `Button`, `Input`, `InputNumber`, `Checkbox`, `Radio`, `List`, `Modal`, `SmartForm`, `Divider`, `Stack`, `Space`, `Tag`, `Tooltip`, `Typography`, `Upload`, `Image`, and `Collapse`.
- Do not introduce shadcn, Radix, Base UI, Tailwind, or a new CSS framework in this phase.
- Keep the route/layout fix visually neutral: order routes should use `OrderRouter`/order-specific naming, but content spacing and navigation behavior must remain stable.
- Order creation must read as one continuous operator flow: customer lookup, inline customer add when needed, selected-customer summary, core order form, compact details, attachments, and save.
- Shipping-code capture must be row-level and compact. Keep the existing modal as a secondary path only if it does not compete with the inline row action.

---

## Spacing Scale

Declared values (must be multiples of 4). Existing code sometimes uses `gap={3}`, `gap={5}`, or small inline margins; new Phase 3 UI should normalize new surfaces to this scale.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, sync-warning sublines, compact selected-customer metadata |
| sm | 8px | Form row gaps, tag groups, inline shipping-code controls |
| md | 16px | Default vertical spacing between create-flow sections |
| lg | 24px | Page-level form groups and list-to-form transitions |
| xl | 32px | Rare separation between lookup and order form on desktop |
| 2xl | 48px | Not used in Phase 3 |
| 3xl | 64px | Not used in Phase 3 |

Exceptions: Existing wrapper/component defaults may remain where changing them would widen scope. Do not add decorative page-section padding or marketing-style spacing.

### Layout Rules

- Customer lookup and selected-customer summary must fit above the order form without creating a new page hero or large card stack.
- Selected-customer summary must be compact: name, phone, province/address preview, and a clear change/search action. It may use a bordered `Card noShadow`, `Alert`, or plain `Stack`, but must not be a large visual container.
- The first visible create form must show: order name, item list, payment amount, note/attachments, and save action.
- Less-common order fields must live in one compact expandable section. The collapsed header must show changed values for priority, free shipping, shipping partner, payment method, COD amount, shipping cost, and important note.
- Order rows must remain scan-friendly. Inline shipping-code entry must not push the primary order name, status tags, payment amount, phone, or address out of view.
- Mobile controls must have tap targets at least 32px high for dense secondary actions and at least 40px high for primary save/paste actions.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 18px | 400 | 1.45 |
| Label | 14px | 500 | 1.35 |
| Heading | 18px | 600 | 1.35 |
| Display | not used | not used | not used |

### Typography Rules

- Keep Ant Design's configured `fontSize: 18` for normal form/list content.
- Use compact labels at 14px only for summaries, tags, helper text, and row-scoped status detail.
- Do not add hero-scale headings in this internal workflow phase.
- Text must not be scaled with viewport width. Use wrapping, ellipsis, or max-width constraints for long customer names, addresses, order names, and shipping codes.
- Button copy must stay short enough to fit on mobile: prefer `Tạo đơn`, `Lưu đơn hàng`, `Dán mã`, `Lưu mã`, `Thử lại`, `Đã xử lý`, and `Đổi khách`.

Accent reserved for: primary create/save actions, focused operator action buttons, and selected active controls where Ant Design already uses `colorPrimary`.

### Status and Semantic Colors

- Preserve existing status colors from `src/Common/Constants/AppConstants.ts`: shipped `#2aa345`, returned/destructive `#990505`, create-delivery `#9b0ead`, waiting-return `#f79a72`, COD-paid `#7B3F00`, free-ship `#1877F2`, priority `#f79a72`, urgent `#3f50eb`.
- Trello sync warning state must use Ant Design warning semantics (`Tag color="warning"` or equivalent) and the existing `OrderSyncStatusWidget` copy/actions.
- Do not add persistent green success badges for normal local/Trello success. Success remains quiet: existing toast plus normal row content.
- Avoid a one-note orange/brown palette. Orange is a primary-action accent, not a background theme.

## Copywriting Contract

All user-facing workflow copy in this phase should remain Vietnamese and operator-direct.

| Element | Copy |
|---------|------|
| Primary CTA | `Lưu đơn hàng` |
| Customer lookup placeholder | `Nhập số điện thoại` |
| Customer not found heading | `Chưa có khách hàng này` |
| Customer not found action | `Tạo khách hàng mới` or existing `Tạo đơn khách mới` if reusing the current widget unchanged |
| Selected-customer change action | `Đổi khách` |
| Compact details section title | `Thông tin thêm` |
| Compact details changed summary | `Đã đổi: {field list}` |
| Attachment empty state | `Chưa có ảnh đính kèm` |
| Shipping-code inline placeholder | `Nhập mã vận đơn` |
| Shipping-code paste action | `Dán mã` |
| Shipping-code save action | `Lưu mã` |
| Create local success + Trello warning toast | Use `getOrderWorkflowMessage(result)` through existing Phase 2 helpers |
| Shipping local success + Trello warning toast | Use `getOrderWorkflowMessage(result)` through existing Phase 2 helpers |
| Row sync retry action | `Thử lại` |
| Row sync manual resolved action | `Đã xử lý` |
| Error state | State the problem and next action, e.g. `Không đồng bộ được Trello. Kiểm tra kết nối rồi bấm Thử lại.` |
| Destructive confirmation | Keep existing delete/return confirmations; do not add new destructive flows in Phase 3 |

### Copy Rules

- Do not add visible instructional text describing keyboard shortcuts, design features, or how the UI works beyond the immediate field/action label.
- Prefer specific verbs over generic copy: `Dán mã`, `Lưu mã`, `Lưu đơn hàng`, `Đổi khách`.
- Empty states must include the next action only when the operator can act immediately.
- Row-scoped sync warnings must name Trello and expose both recovery actions: `Thử lại` and `Đã xử lý`.

## Interaction Contract

### `/order/create`

- Direct navigation to `/order/create` must show customer lookup immediately when no `customerId` is provided.
- When a known `customerId` is provided through route state, show the selected-customer summary and order form immediately.
- Phone lookup must reuse the existing phone-search behavior. If no matching customer is found, new-customer entry must happen inline inside the create flow, then continue directly to the order form.
- Selecting or creating a customer must not navigate away from `/order/create`.
- The selected-customer summary must remain visible while editing the order and must support changing the customer without losing intentional form edits unless the implementation explicitly resets affected customer-derived fields.
- Attachments remain part of the core form and should use a compact add/preview area. Preview image dimensions should stay stable around 96-100px square.
- Saving an order must keep current behavior: local save, Trello card creation, attachment upload, then navigate back to order list on local success.
- If local create succeeds but Trello card or attachment sync fails, navigate back to the order list, show a warning toast, and rely on row-scoped sync status for persistent recovery.

### Order Row Shipping-Code Entry

- For orders eligible for shipping-code entry, expose an obvious row-level quick action/input using the barcode/truck icon vocabulary already present.
- Inline entry must include an explicit `Dán mã` action. Do not auto-read clipboard when the row input opens.
- `Lưu mã` must call the existing `useOrder.changeShippingCode(order.id, code)` workflow and must not bypass Phase 2 local-first failure recording.
- When local save succeeds, the row must immediately show the saved shipping code even if Trello comment/move fails.
- If Trello sync fails, show the existing compact warning with `Thử lại` and `Đã xử lý` on that order row.
- Normal success should not add persistent success indicators.

## Screen Contracts

### Order List

- Keep search, status filters, COD filters, totals, and pagination in their current dense order.
- Replace the add-order modal handoff with navigation or direct entry to `/order/create` only if the create screen owns lookup/add-customer behavior.
- Do not add a list-wide sync alert center in this phase.
- Row content priority: order name, status/payment/priority tags, row sync warning if present, amount/COD, shipping code, phone, address, action buttons.

### Order Create

- Keep a single-column mobile-first form flow. Desktop may use tighter grouping, but do not create a multi-column dashboard-style form that breaks mobile parity.
- Core-first fields: selected-customer summary, order name, placed items, payment amount, note, attachments, save action.
- More-details fields: priority, free shipping, shipping partner, payment method, COD amount, shipping cost, important note.
- The more-details collapsed summary must surface non-default values using tags or short text so hidden changes remain visible.

### Shipping-Code Row UI

- Prefer an extracted widget if it keeps `OrderItemWidget` readable, but the visual contract is row-level and compact either way.
- Keep the existing focused modal as a secondary action if retained; remove or suppress its auto-clipboard behavior when used for the new fast path.
- Loading state must be local to the row/input/button being saved.
